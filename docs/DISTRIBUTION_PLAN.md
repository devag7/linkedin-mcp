# Distribution experiments and measurement

The 10,000-star ambition is a planning target, not a promised result. Prioritize
users who complete a useful workflow. Source changes, guides and metadata are
prepared locally; no release, listing submission, social post, direct message,
Discussions change or campaign was executed in this task.

| Order | Concrete artifact | Measure / gate | Current state |
| --- | --- | --- | --- |
| 1 | Generated capability table, truthful setup and troubleshooting | First-use protocol; target 80% read in 15 min, real sample required | Prepared; volunteers untested |
| 2 | 90-second walkthrough: version → doctor → cold whoami → one bounded search → provenance → close | Reproducible supported client/OS, no credentials/content published | npm run demo:offline and dated actual local output prepared; real read demo outstanding |
| 3 | Job/company research and reviewed-post guides | Voluntary workflow completion, manual retries, relevant referrals | WORKFLOWS.md prepared; no completion measurement |
| 4 | Verified client install matrix | Per-client version/OS/run evidence; remove stale claims | SDK transports tested; client applications untested |
| 5 | Contributor/issue loop, roadmap and changelog | Median response time, returning contributors, repeat useful workflows | Local community artifacts updated; remote settings/issues unchanged |
| 6 | Registry/directory verification and substantive tutorial | Actual accepted listing/version, qualified referrals and first reads | Metadata generated and validated against pinned official schema; listing acceptance/publication pending |
| 7 | Factual release story | One solved problem + exact evidence + limit + reproducible example | Unreleased changelog prepared; publishing separate |

Monthly report template: month, artifact/version, consenting first-use attempts,
first-read success/15-minute rate, sample size by client/OS, voluntary recurring
workflow count, response time, contributor participation, permitted aggregate
referral counts and net stars. Leave unavailable metrics blank; never substitute
mock counts or scraped member identities. Use GitHub's supported aggregate
repository information after confirming current API/docs and access. Do not add
runtime network analytics for this purpose.

Review at 30/60/90 days: poor first-use → repair setup before promotion; useful
repeat use with weak reach → improve explanations/discoverability; weak setup and
reuse → interview willing users and revisit positioning. Budget maintainer time
for endpoint change, support and documentation before promising response SLAs.
Official app ownership/maintenance capacity remain maintainer decisions.
